## 0. 요약

**목표.** 현실 세계와 최대한 같은 물질·반응·수량으로 *"무엇이든 만들 수 있다"*를 구현하는 생산 모델 **Uranus**. 원자에서 출발해 분자 → 생체 분자 → 전자 부품 → 생명체로 올라가고, 끝에는 세상에 없는 것까지 만든다. **제조·합성은 팩토리오처럼 "재료가 있으면 레시피대로 만든다"**로 추상화한다.

**설계의 축.** 현실성은 *데이터*가, 단순함은 *규칙*이 맡는다.
- 데이터: 실제 화학식·반응식·수량·부품 구성을 쓰고, 검증기로 원자 보존·질량·도달 가능성을 자동 확인한다.
- 규칙: `재료 + 시간 → 결과물`. 온도·압력·반응 속도 같은 물리 시뮬레이션은 하지 않는다.

**현재.** 플레이 가능한 방치형 제작 게임 프로토타입(**MachineFree**). 레시피 110개, 생성기 10개. 수소 15개로 시작해 기초 화학 레시피 34개와 생성기 10개까지는 도달하지만, 생물·전자 분기(66개)와 원료 가공 일부(4개)는 재료 공급원이 없어 막혀 있다.

**가장 큰 걸림돌**
1. **수량 타입**: `decimal`(최대 7.9×10²⁸)에 `int` 캐스팅까지 섞여 있다. 지금 데이터대로면 CCD 1개에 이산화규소만 약 10²⁸개가 들어가므로, 현실 수치를 담을 수 없는 구조다.
2. **식별자**: 한국어 이름이 곧 ID다. 띄어쓰기만 다른 이름이 벌써 3쌍 있다.
3. **코어가 WPF에 묶여 있음**: UI 스레드 없이는 인벤토리도 못 쓴다. 테스트도, 밸런스 시뮬레이션도 돌릴 수 없다.
4. **데이터 형식**: 가로형 엑셀은 재료 칸이 17개로 고정인데, CCD가 이미 17칸을 다 쓴다.

**권장 순서.** M0 정리 → **M1 모델·데이터·현실성 검증기** → M2 헤드리스 시뮬레이션·세이브 → M3 MVVM UI → M4 게임 루프(규모 사다리) → M5 콘텐츠.
레시피를 더 늘리기 전에 M1~M2부터 끝내야 나중에 옮기는 비용이 커지지 않는다. 코어가 약 1,050줄인 지금이 구조를 바꾸기 가장 싼 때다.

**확정된 결정** (2026-10-12, 자세한 내용은 8장)
- 생산량이 1보다 작은 결과물(예: 0.2)은 소수로 누적한다. 0.2면 5번 만들 때 정확히 1개가 되고, 난수는 쓰지 않는다.
- 생성기는 종류마다 여러 대 가질 수 있고, 생산량은 보유 수에 비례한다.
- 데이터 원본은 YAML로 옮긴다.

## 1. 목표

### 1.1 두 원칙

| | 현실을 따른다 (데이터) | 팩토리오를 따른다 (규칙) |
|---|---|---|
| 범위 | 물질, 화학식, 반응식, 수량, 부품 구성, 원료를 얻는 방법 | 제작 방식, 제작 시간, 대기열, 생성기 |
| 방법 | 실제 값을 쓰고 출처를 주석으로 남긴다. 검증기가 자동으로 확인한다 | 재료가 있으면 레시피대로 제작한다 |
| 하지 않는 것 | 게임 편의용 임의 비율. 꼭 써야 하면 `approximate`로 표시해 둔다 | 온도·압력·반응 속도·수율 같은 물리 시뮬레이션 |

### 1.2 데이터는 이미 이 원칙을 따르고 있다

- **화학**: 메탄 연소 `CH4 + 2O2 → CO2 + 2H2O`, 황산 공정 `S → SO2 → SO3 → H2SO4`, 습식 인산 공정 `수산화인회석 + 5H2SO4 → 3H3PO4 + 5CaSO4 + H2O`. 대부분 원자 수가 맞는다.
- **생물**: rRNA의 리보스 수가 염기 수의 합과 같다. 23S rRNA는 2,904 = A838 + C404 + G727 + U935로 대장균 23S 길이와 같다. 40S = 18S rRNA + 리보솜 단백질 33개.
- **전자**: CCD = 감광성 다이오드 2,073,600개(1920×1080). 8인치 웨이퍼 = 규소 1.133×10²⁴개로, 직경 200mm·두께 약 0.72mm 웨이퍼의 실제 원자 수와 맞는다.
- **장기 목표**: 진핵세포·원핵세포·핵양체·DNA가 재료 없이 미리 등록돼 있다.

### 1.3 원칙에서 벗어난 곳 (검증기가 잡아야 할 종류)

- **원자 수 불일치**: `에탄 150 + 수소 300 → 에틸렌 150`. 실제 반응에서는 에탄에서 수소가 *나온다*.
- **게임식 비율**: `구리광석 60 + 산소 60 + 탄소 60 → 구리 600`, `원유 + 가스 → 석유`. 광석을 실제 광물(예: 황동석 CuFeS₂)로 정의하면 제련도 반응식으로 쓸 수 있다.
- **규모 오류**: 크리스탈 1개가 이산화규소 3×10²⁴개, 약 300g이다(실제 수정 진동자 블랭크는 mg 단위). CCD 안의 시프트 레지스터 3,000개가 각각 클록 회로를 갖고 클록 회로마다 크리스탈이 들어가서, **CCD 1개에 이산화규소 9.8×10²⁷개(약 1톤)가 필요**하다. 감광성 다이오드(픽셀)마다 광학 창이 따로 붙은 구조도 같은 종류의 문제다. 실제 CCD는 칩 전체에 창이 하나다. 질량 검증 규칙이 있었다면 바로 드러났을 문제다.
- **단위 혼재**: 수소·규소의 1은 "원자 1개", 저항·커패시터의 1은 "부품 1개"다. 구리광석은 단위가 정의돼 있지 않다.

### 1.4 제품 구조

```
Uranus (지식 + 규칙)   아이템·레시피·생성기 데이터와 레시피 그래프 계산
                       (필요 원료, 도달 가능성, 원자 보존, 질량)
 ├─ MachineFree        Uranus를 플레이하는 첫 번째 게임. 방치형 제작 게임
 └─ (선택) Explorer    도감·계산기. "CCD 하나에 원자가 몇 개, 몇 그램 필요한가"
```

MachineFree 창은 820×600 크기에 화면 왼쪽 아래(`Top=750, Left=0`)로 고정돼 있다. 화면 구석에 띄워 두는 데스크톱 방치형을 염두에 둔 것으로 보인다.

## 3. 목표 아키텍처

### 3.1 솔루션 구조

```
Uranus.sln
├─ data/                        콘텐츠 원본 (텍스트라 diff·리뷰 가능)
│  ├─ elements.yaml             원소, 원자량
│  ├─ items/                    분야별 아이템
│  ├─ recipes/                  분야별 레시피
│  └─ generators.yaml
├─ src/
│  ├─ Uranus/                   지식 모델 (UI·파일 형식과 무관)
│  │                            ItemId, ItemDef, RecipeDef, GeneratorDef, UranusDatabase,
│  │                            RecipeGraph(생산처·소비처 색인, 도달 가능성, 필요 원료),
│  │                            Formula(화학식 파싱, 원자 보존, 질량)
│  ├─ Uranus.Data/              YAML 로더 + Validator(규칙별 오류·경고)
│  ├─ MachineFree.Core/         게임 규칙 (헤드리스): GameState, Simulation.Tick(dt), 세이브 v2, 오프라인 진행
│  └─ MachineFree/              WPF: View + ViewModel(CommunityToolkit.Mvvm)
├─ tools/Uranus.Tools/          CLI: migrate(xlsx→yaml), validate, graph, simulate
└─ tests/                       Uranus.Tests, MachineFree.Core.Tests (xUnit)
```

참조 방향:

```
MachineFree(WPF) ─→ MachineFree.Core ─→ Uranus
       └──────────→ Uranus.Data ──────→ Uranus
Uranus.Tools ─────→ Uranus.Data
```

**`Uranus`와 `MachineFree.Core`는 WPF도 EPPlus도 참조하지 않는다.** 프로젝트 수가 부담되면 `Uranus.Data`를 `Uranus`에 합쳐도 된다. 꼭 지킬 것은 "UI 없는 코어"와 "도구·테스트" 두 가지다.

### 3.2 핵심 설계 결정

| 주제 | 지금 | 바꿀 방향 | 이유 |
|---|---|---|---|
| 식별자 | 한국어 이름(`KoreanName`) | 불변 ID + 표시 이름 `{ko, en}`. 화학 물질은 화학식(`H2O`), 나머지는 영문 snake_case(`rrna_23s`) | 이름을 바꿔도 세이브가 깨지지 않고, 다국어가 가능하다 |
| 수량 | `decimal` + `int` 캐스팅 | `double`(최대 1.8×10³⁰⁸), 표시는 포맷터 한 곳에서 | CCD 1개의 원료가 이미 10²⁸ 단위이고, 사람 1명은 원자 약 7×10²⁷개다. 2⁵³(약 9×10¹⁵)까지는 정수도 정확하다. 방치형 장르의 표준 선택 |
| 질량·원자 | 없음 | 원자량 + 화학식으로 분자 질량, 부품은 BOM으로 질량 계산 | 원자 보존·질량 검증, 도감·툴팁의 g/kg 표시 |
| 1 미만 생산량 | 0.2를 "20% 확률로 1개"로 처리 | 소수 그대로 누적. 0.2면 5번에 정확히 1개. 칸에는 정수 부분과 다음 1개까지의 진행도를 표시 | 난수 없이 결정적이라 테스트·오프라인 계산이 쉽다. 수량이 커질수록 현실의 수율(기댓값)과 같아진다 |
| 생성기 | 종류당 1대 전제, 보유 여부만 판정, 매초 확률로 1개 | 종류당 여러 대, 보유 수 × 초당 생산량 × dt, 소수는 누적 | 기계가 많으면 많이 만든다는 현실 규칙. 폭주를 막는 비용 증가는 밸런스 레버로만 쓴다(6.1) |
| 부동소수점 | 해당 없음 | 수량 비교·표시에 작은 허용오차(예: 1e-9)를 둔다 | 0.1을 10번 더하면 0.9999999999999999라서 그냥 내림하면 0개가 된다. 단위 테스트로 고정한다 |
| 데이터 형식 | 가로형 xlsx, 실행 때마다 CSV 변환 | YAML(분야별, 출처 주석) → 로드 + 검증 | 칸 수 제한이 없고 diff가 된다 |
| 코어와 UI | 모델이 `INotifyPropertyChanged`·`ObservableCollection`·애니메이션 상태를 가짐 | 모델은 순수 C#, 변경은 이벤트로 알리고 바인딩 상태는 ViewModel에 | 테스트, 시뮬레이터, 다른 UI 이식 |
| 시간 | 틱마다 0.1초 고정 | `Tick(double dt)`에 실제 경과 시간 전달, 큰 `dt`에서도 여러 개 완성 | 정확도, 오프라인 진행 |
| 세이브 | 객체 그래프 통째로, 한국어 이름, 작업 폴더에 저장 | `version`, ID → 수량 맵, 대기열은 레시피 ID + 진행도, UTC 저장 시각, 임시 파일에 쓴 뒤 교체, 백업, `%LOCALAPPDATA%\MachineFree`에 저장 | 데이터를 바꿔도 안전하고 파일 손상에 강하다 |
| 엑셀 | 실행 중 EPPlus 사용 | 1회성 마이그레이션 도구에서만 쓰고 제거 | 실행 의존성과 라이선스 부담 제거 |

### 3.3 코드 스케치

```csharp
// Uranus: UI 의존성 없음
public readonly record struct ItemId(string Value);
public readonly record struct RecipeId(string Value);

public sealed record ItemDef(ItemId Id, LocalizedText Name, ItemUnit Unit,
                             string? Formula = null, bool IsFictional = false);
public sealed record ItemAmount(ItemId Item, double Amount); // 1 미만이면 소수로 누적
public sealed record RecipeDef(RecipeId Id, double Time,
                               IReadOnlyList<ItemAmount> Inputs, IReadOnlyList<ItemAmount> Outputs);
public sealed record GeneratorDef(ItemId Id, RecipeId Build, IReadOnlyList<ItemAmount> OutputPerSecond);

// MachineFree.Core: 헤드리스
public sealed class Simulation(UranusDatabase db, GameState state)
{
	public bool TryEnqueue(RecipeId recipe, int count) { /* 재료 차감 + 대기열 */ }
	public void Cancel(int queueIndex, int count) { /* 환불 */ }

	public void Tick(double dt) // 실제 경과 시간(초)
	{
		ProduceFromGenerators(dt); // 보유 수 × 초당 생산량 × dt, 소수는 누적
		AdvanceQueue(dt);          // dt 안에 끝나는 만큼 while로 모두 완성
	}
}
```

## 5. 데이터 스키마 (YAML, 구현됨)

```yaml
# data/elements.yaml: 원자량은 질량 계산과 검증에 쓴다
elements:
  - { symbol: H,  name: { ko: 수소, en: Hydrogen }, mass: 1.008 }
  - { symbol: Si, name: { ko: 규소, en: Silicon },  mass: 28.085 }

# data/items/chemistry.yaml: 파일 머리의 category·unit이 기본값. 화학 물질은 화학식이 곧 ID
category: chemistry
unit: particle
items:
  - { id: H2O, name: { ko: 물, en: Water }, formula: H2O }
  - { id: OH-, name: { ko: 수산화 이온, en: Hydroxide ion }, formula: OH- }

# data/items/electronics.yaml: 부품은 piece 단위, 질량은 레시피에서 자동 계산
category: electronics
unit: piece
items:
  - { id: wafer_8in, name: { ko: 8인치 실리콘 웨이퍼 }, expected_mass: [45g, 60g], note: "실제 약 53g" }

# data/recipes/chemistry.yaml
category: chemistry
recipes:
  - id: methane_combustion          # CH4 + 2O2 → CO2 + 2H2O
    name: { ko: 메탄 연소 }
    time: 0.4
    in: { CH4: 1, O2: 2 }
    out: { CO2: 1, H2O: 2 }
  - id: apatite_separation          # 천연 인회석은 세 성분이 섞인 고용체 → 1/3씩
    time: 0.03
    in: { apatite: 1 }
    out: { hydroxyapatite: 1/3, fluorapatite: 1/3, chlorapatite: 1/3 }

# data/recipes/biology.yaml
recipes:
  - id: mrna
    time: 0                         # 아직 미정 → 검증기 경고
    in: { ribose: 1433, adenine: 396, cytosine: 317, guanine: 392, uracil: 328 }
    out: { mrna: 0.2 }              # 1 미만은 소수로 누적: 5번 만들면 1개

# data/generators.yaml: 생성기 아이템과 build_<id> 레시피가 함께 만들어진다
generators:
  - id: hydrogen_synthesizer
    name: { ko: 수소 합성기 }
    build: { time: 12, in: { H: 15 } }
    produces: { H: 0.25 }           # 1대당 초당

# data/game.yaml
start:
  inventory: { H: 15 }
generator_cost_growth: 1.15
offline_cap_hours: 24
```

실제 공정 기반 생성기의 예(아직 데이터에 없음):

```yaml
  - id: air_separator
    name: { ko: 공기 분리기 }
    build: { time: 30, in: { Fe: 100, Cu: 50 } }    # 값은 예시
    produces: { N2: 0.78, O2: 0.21, Ar: 0.0093 }    # 공기 조성 비율
```

- 수량은 정수·소수·지수(`1.133e24`)·분수(`1/3`) 표기를 받는다. 분수는 YAML에서 문자열로 읽히므로 로더가 직접 해석한다.
- ID는 한 번 정하면 바꾸지 않는다. 표시 이름은 자유롭게 바꿔도 된다.
- 출처와 근거는 주석으로 남긴다. 실측 기반 데이터의 신뢰도를 지키는 장치다.
- 표시 플래그:
  - 가상 아이템: `fictional: true`
  - 게임식 비율 레시피: `approximate: true`(원자 보존 검사를 건너뛴다)
  - 목표용 플레이스홀더: `goal: true`
- 스프레드시트가 계속 편하다면 세로형 시트(레시피 1행 + 입출력 1행씩)로 바꿔도 된다. **검증기가 파일이 아니라 로드된 모델을 검사**하게 만들면 형식을 무엇으로 정하든 그대로 쓸 수 있다.

## 6. 게임 디자인 (MachineFree)

### 6.1 핵심 과제: 수십 자릿수를 건너는 규모 사다리

지금 수소는 초당 0.25개씩 생기는데, 웨이퍼 한 장에는 규소가 1.13×10²⁴개 필요하다. 현실 수치를 지키면서 게임이 되려면 아래 두 병목을 모두 지수적으로 넓혀야 한다. 방치형(인크리멘털) 장르가 바로 이 문제를 다룬다.

**① 원료 공급: 생성기**
- 생성기는 종류마다 여러 대 가질 수 있고, 생산량은 보유 수에 비례한다(확정).
- 비용이 고정이면 너무 빨리 커진다. 수소 합성기는 수소 15개로 만들고 초당 수소 0.25개를 낸다. 제작 대기열이 병목이 아니라면(②를 넓힌 뒤라면), 번 수소를 전부 재투자할 때 약 42초마다 2배가 되어 1시간이 안 돼 10²⁴개에 이른다.
- 그래서 브레이크가 하나 필요하다. 기본안은 보유 수에 따라 비용이 오르는 방식(예: ×1.15ⁿ)이다. 이건 데이터가 아니라 게임 규칙이므로 생성기마다 배율을 두고 시뮬레이터로 조정한다. 더 현실적인 대안은 팩토리오식 전력 제약이다. 생성기마다 전력을 쓰고 발전량이 상한이 된다. M4 이후에 검토한다.
- 티어별 배율 업그레이드(×10, ×1,000 …)도 함께 쓴다.

**② 제작 처리량: 대기열**
- 지금 제작은 한 번에 1개씩, 정해진 시간이 걸린다. 물 1개에 0.1초면 10²⁴개에는 10²³초가 걸린다. 원료가 아무리 많아도 제작이 따라가지 못한다.
- **규모 단계 해금**: 입자 → 나노몰 → 마이크로몰 → 몰. 예를 들어 "아보가드로" 마일스톤을 넘으면 레시피 1회가 몰 단위(×6.022×10²³)로 돈다. 현실의 개념을 그대로 진행 장치로 쓰는 방식이다.
- 병렬 대기열과 자동 반복으로 처리량을 더 넓힌다(6.2).

**표시**
- 개수 옆에 mol과 질량(g, kg)을 함께 보여 주면 규모가 체감된다. 예: 물 6.02×10²³개 = 18.0g.
- 1 미만으로 쌓인 소수는 칸에 진행도로 보여 준다. 예: mRNA 0.6개면 "0"과 60% 막대.

## 7. 콘텐츠 확장: 현실의 공급망을 따라간다

1. **원료를 실제 공정으로 얻기**: 공기 분리(질소 78%·산소 21%·아르곤 0.9%), 해수 증발(염화 나트륨 등), 채굴(실제 광물 화학식), 유정(원유·천연가스). 질소 공급원이 생기면 생물 분기가 열린다.
2. **막힌 원소 풀기**: 생성기가 없는 기본 원소 7종(질소·규소·갈륨·비소·인듐·알루미늄·붕소)과 인. 예를 들어 규소는 석영(SiO₂) 환원 같은 실제 경로로 만들 수 있다.
3. **생물**: 리보스(C₅H₁₀O₅)·아데닌(C₅H₅N₅)·시토신(C₄H₅N₃O)·구아닌(C₅H₅N₅O)·우라실(C₄H₄N₂O₂)을 원자에서부터 만든다 → RNA → 리보솜 → 아미노산·단백질 → DNA → 원핵세포 → 진핵세포.
4. **전자**: 막힌 부품 10종(트랜지스터·마이크로컨트롤러·인덕터·전압 레귤레이터·연산 증폭기·송수신기·온도 센서·온도 조절기·팬·히터)을 채운다. P형/N형 반도체는 이미 있으니 트랜지스터부터 시작한다. 그다음 CCD → 카메라 같은 완제품으로 간다. 크리스탈과 픽셀별 광학 창 같은 규모 문제도 이 단계에서 고친다.
5. **세상에 없는 것**: 실제 티어 위에 `fictional: true` 티어를 얹는다. 실제 재료를 넣어야만 만들 수 있게 해서 "현실에서 출발해 현실 너머로" 가는 흐름을 지킨다.

콘텐츠 작업은 `validate`를 오류 없이 통과하고 도달 가능성 리포트를 확인해야 완료로 본다.

## 8. 결정 사항

### 8.1 확정 (2026-10-12)

| 주제 | 결정 | 이유 |
|---|---|---|
| 목표 | 현실 데이터 + 팩토리오식 제작 | 프로젝트 소유자 확인 |
| 1 미만 생산량(예: RNA 0.2) | 소수로 누적한다. 0.2면 5번 만들 때 정확히 1개가 되고, 난수는 쓰지 않는다 | 원래 의도("5번 중 1개")와 같은 결과를 결정적으로 낸다. 테스트·오프라인 계산이 쉽고, 수량이 커질수록 현실의 수율과 같아진다 |
| 생성기 | 종류마다 여러 대, 생산량은 보유 수에 비례 | 기계가 많으면 많이 만든다는 현실 규칙. 폭주를 막는 비용 증가는 밸런스 레버(6.1) |
| 데이터 형식 | YAML | 칸 수 제한이 없고, diff·주석이 된다 |

| 질문 | 가정 |
|---|---|
| 원자 보존 위반은 오류인가, 경고인가? | 화학식이 있는 아이템끼리는 오류, 그 밖은 경고. 게임식 비율은 `approximate`로 표시하면 허용 |
| 제작 시간도 현실값을 따르나? | 아니다. 시간은 밸런스용 추상값 |
| 공개 배포(Steam 등) 계획이 있나? | 당분간 개인 프로젝트. 공개하게 되면 EPPlus를 완전히 빼고 플랫폼을 다시 검토 |
| Windows 데스크톱(WPF)을 유지하나? | 유지. 코어를 분리해 Avalonia·웹으로 옮길 여지만 남긴다 |

## 부록. 분석 방법

- 코드 전체를 읽고, GitHub API로 저장소 메타데이터·커밋·브랜치·이슈를 확인했다.
- 엑셀 2개를 직접 파싱해 레시피 그래프를 분석했다. 도달 가능성은 "재료가 존재하는가"만 보고 수량은 따지지 않았다. CCD 소요량은 아이템마다 기본 원소 기준으로 가장 싼 레시피를 고르고 부산물은 무시해 계산했다.
- 원본을 복사한 폴더에서 솔루션을 빌드했고, 코어 라이브러리를 참조하는 콘솔 하네스로 2.4의 "실행" 항목을 재현했다. 원본 폴더는 이 문서를 추가한 것 말고는 건드리지 않았다.
